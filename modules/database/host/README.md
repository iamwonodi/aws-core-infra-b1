# Database Domain Module

This module is the database layer: a single consolidated database host in the isolated tier, the secret it uses for its own administrator credentials, its EC2 auto-recovery alarm, its private DNS record, and its automated backup policy.

If you're new to this repo: think of this module as answering **"where does the application's data actually live, how does it get its credentials, and what keeps it alive?"** Everything about what talks to the database (the compute fleets) lives in `compute`; everything about how a request even reaches this project lives in `edge`. This module doesn't scale, doesn't serve traffic, and isn't reached by CloudFront or the internet at all -- it's a single host, on purpose (see below).

---

## Why this is a single instance, not a fleet

Every other compute resource in this project (see the `compute` module) is an Auto Scaling fleet. The database deliberately isn't. Databases aren't stateless the way application servers are -- scaling them isn't a matter of adding more identical, disposable instances the way it is for a web server. This module creates one host, with an optional secondary data volume for actual database storage, and leaves real high-availability database architecture (replicas, managed database services, etc.) as a deliberate future decision rather than something this module tries to solve on its own.

Recovery from failure is instead handled by EC2 auto-recovery (see below), not by replacing the instance -- that distinction is why several other design choices in this module (a Terraform-managed DNS record instead of self-registration, no ASG) are what they are.

## What this module creates

### Secrets vault

A random 32-character administrator password (letters, digits and `-_.` only, so it survives the env files it passes through), generated by Terraform and stored in the secrets vault -- never written into any rendered configuration or user-data script. Only the secret's ARN is passed to the database host, which fetches the actual value from Secrets Manager itself at runtime.

### The database profile and host

`database_profile` is the IAM role/instance profile the database host runs as -- separate from any fleet's own profile in the `compute` module. `database` (the `compute-storage` module) is the actual EC2 instance: placed in the first isolated subnet, running the same shared AMI the `compute` module built, with an optional secondary EBS volume for persistent storage.

### SSM parameters

`aws_ssm_parameter.database_connection_limits` holds `connection_limits` (core's `data/connection-limits.json`) under `/<project>/database/connection-limits`, which the provisioning scripts read on every run; see *Connection limits* below.

`aws_ssm_parameter.database_host_instance_id` publishes the database host's instance ID under `/project/database-hub/instance-id`, so other tooling (deployment scripts, runbooks) can look it up without needing to query Terraform state directly.

### EC2 auto-recovery

A CloudWatch alarm on `StatusCheckFailed_System`, triggering `ec2:recover` when the underlying hardware is impaired. This is the correct recovery mechanism for a single stateful instance -- not an Auto Scaling Group. The data volume is a separately Terraform-managed EBS resource attached by instance ID; an ASG-driven replacement instance would need that volume reattached by something outside Terraform's own apply cycle, since ASG replacement happens on AWS's own schedule, not Terraform's. Auto-recovery instead preserves the same instance ID, private IP, and attached volumes -- confirmed directly against AWS's own documentation -- so nothing else in this module needs to react to a recovery event at all.

Covers hardware-level failure specifically (an impaired underlying host), not an OS-level hang that doesn't trip that check, and not accidental manual termination. Period is `300` seconds, matching EC2's free basic-monitoring interval -- narrowing it without also enabling detailed monitoring (~$2.10/instance/month) doesn't speed up detection, since basic monitoring only emits a new data point every 300 seconds regardless of the alarm's own period.

### Private DNS record

A Terraform-managed `A` record (via the `route53-record` module), not a self-registering boot script. This is correct specifically because of the auto-recovery alarm above: the private IP stays stable across every realistic failure/replacement scenario (auto-recovery preserves it; a Terraform-triggered replacement updates this record in the same apply, since it depends on `module.database.private_ip` directly). A static record needs no IAM permission on the instance itself, and is correct the moment `terraform apply` finishes -- before the instance has even booted.

### Automated backups

A DLM (Data Lifecycle Manager) lifecycle policy, taking daily snapshots of the persistent data volume, retained for `db_backup_retention_days` (default 7). Deliberately DLM rather than AWS Backup -- AWS Backup's extra features (cross-region copy, centralized multi-account policies, legal-hold vaults) are aimed at production compliance and DR needs this development environment doesn't have.

Two real limitations worth knowing, not just implementation detail:

* **Crash-consistent, not application-consistent.** This backs up the volume at the block level -- equivalent to recovering from a sudden power loss, not a clean shutdown. Modern journaling engines (InnoDB, Postgres WAL, WiredTiger) generally recover fine from this, but it's a real, different guarantee than a coordinated database-level backup.
* **Cannot restore just one service team's data.** Multiple teams' databases share this one host and volume -- a restore brings back everything together. If per-team granular restore ever becomes a real need, the next step is per-team logical dumps (`mysqldump`/`pg_dump`/`mongodump`) to S3 *alongside* this, not a replacement for it.

`db_enable_automated_backups` and `db_enable_data_volume_mount` both have to be true for this to actually do anything -- there's nothing to snapshot without a data volume.

The policy targets the data volume by its `Name` tag (computed in `locals.tf` to exactly match what the `terraform-aws-ebs` module itself applies), because `compute-storage` has no tag pass-through of its own to inject a distinguishing tag through directly. If that naming pattern ever changes in the `ebs` module, it needs to change here too.

## How database engines are deployed

The **platforms team** owns the database engines. This module does not know about any particular engine and generates no compose files. It provides the host, the persistent data volume, the secret, and the deploy mechanism; the platforms team publishes what should run.

### What the platforms team publishes

To the fleet deploy bucket (owned by the `compute` module):

```text
database/engines/<engine>/docker-compose.yaml     (or docker-compose.yml)
database/engines/<engine>/.env
database/registry.json
```

```json
{
  "postgres": { "port": 5432, "active": true },
  "mysql":    { "port": 3306, "active": false }
}
```

**Publish the engine folders first and `registry.json` last.** An engine that is not in the registry is never started, so a half-finished upload cannot start anything. Then send the `<project>-database-update` SSM document (output `update_document_name`) to run the deploy. The host also runs a deploy once at boot; with no registry published that is a successful no-op.

### What starts and stops an engine

| Change | Effect |
| --- | --- |
| `"active": true` (or omitted) | Deployed with `docker compose up --wait`, as project `db-<engine>` |
| `"active": false` | Stopped with `docker compose stop`; data is kept |
| Entry removed from the registry | Left running, untouched |
| Folder removed from S3 | Left running, untouched (a registered engine with no folder is reported as a failure) |

A database must never stop as a side effect of a file disappearing. This differs from the fleet, where removing a service stops it. Nothing in this module ever runs `down`, `down -v` or `rm`, and data lives on the persistent volume regardless.

### What an engine's compose file can rely on

| Name | Meaning |
| --- | --- |
| `${DATA_ROOT}` | Persistent data root on the data volume. Keep data in `${DATA_ROOT}/<engine>` |
| `${ENGINE_NAME}` | The engine's folder name |
| `${ENGINE_PORT}` | The port from the registry, which is the engine's native port. Publish it: `"${ENGINE_PORT}:5432"` |

The compose file loads its environment with `env_file: .resolved/.env`, the secret-resolved scratch copy. In the engine's `.env`, secrets are referenced by pointer, and `CORE_ROOT_SECRET_ARN` (the ARN of the database administrator secret) is provided by the platform:

```env
POSTGRES_PASSWORD=__FROM_SECRET__:CORE_ROOT_SECRET_ARN:root_password
```

`DATA_ROOT`, `ENGINE_NAME`, `ENGINE_PORT` and `CORE_ROOT_SECRET_ARN` are reserved: an engine `.env` may not define them.

### The compose guard

Before an engine starts, its compose file is rendered with `docker compose config` and rejected if it uses privileged mode, added capabilities, devices, host namespaces or the Docker socket, or bind-mounts anything outside its own folder and `DATA_ROOT`. That last rule is the data-safety net: a data directory that is **not** on the persistent volume is refused, instead of silently losing data when the instance is replaced. It is a best-effort deny-list, not a security boundary.

### Images must come from ECR

The database host sits in the isolated tier, which has no internet path, so it cannot pull from Docker Hub. With `db_require_ecr_images = true` (the default) an image from any other registry is rejected up front with a clear message instead of timing out on a pull. To use a public image, mirror it into ECR (an ECR pull-through cache works) and reference it from there.

### Registry validation

`update.sh` validates the registry before acting on it and leaves the previous one in place if it is bad: it must be a JSON object; each engine needs a lowercase name (letters, digits, hyphens), an integer `port` from 1024 to 65535, and an optional boolean `active`; no two **active** engines may share a port. The platforms repository's CI enforces the same rules, plus that each engine is published on its own native port (host port = engine port) and that every registered engine has a folder.

### Ports and the security group

Each engine's port is opened on the isolated security group by the engine's own pipeline, and published as an SSM parameter for services to read. This module does not create those rules.

### Scripts, checksums and refresh

The scripts live in the deploy bucket under `_platform/` and are verified against a checksum manifest in SSM (`/<project>/database/scripts-manifest`) before anything is installed. The manifest holds the checksums, not the user data, so **editing a script never restarts the database host**. To update scripts on the running host, send the `<project>-database-refresh-scripts` document. `provision.sh` (which creates a service's database and user inside an engine) is one of these scripts.

### Data volume

Bootstrap formats the persistent volume only when it carries no filesystem, mounts it by UUID with `nofail`, and finds the device even when it appears as an NVMe disk (`/dev/nvme1n1`) rather than the configured `/dev/sdb`. If more than one unmounted EBS disk exists it refuses to guess.

### People's logins

`provision-people.sh` makes each running engine's people logins match their list, at two scopes, exactly as the managed databases' provisioning functions do:

| Scope | Logins | Reach | List | Run by |
| --- | --- | --- | --- | --- |
| `platform` | `platform.<name>` | every service's database | core's people secret, `<project>-database-people-<environment>-secret-vault` | the `<project>-database-provision-people` SSM document (sent by core's apply, after refreshing the scripts), and after every service |
| `service` | `<service>.<name>` | that service's database only | the `agents` entry of the service's own secret | `provision-service.sh`, whenever the service is provisioned |

Access is given through each scope's groups with default privileges on PostgreSQL, direct grants on MySQL, and `read` / `readWrite` (agents) or `readAnyDatabase` / `readWriteAnyDatabase` (platform) on MongoDB. A login of the scope no longer listed is removed; which logins are the scope's is decided by an exact pattern, never by `LIKE`, where `_` in a service's name is a wildcard. Everything read from a secret is checked against core's patterns before any of it reaches an engine. Tests: `modules/platform/host-scripts/tests/test_people.sh` (offline) and `test_people_real.sh` (real PostgreSQL and MySQL, when the provisioning function's test variables are set).

## Correctness fixes made while building this module

*(The original `bootstrap.py` compiler and `engine-map.json` were removed when the platforms-team model above replaced them; `provision.sh` now finds a container by its Compose project label.)*

**A missing `.env` template, and a `.gitignore` collision.** The database bootstrap process needs a rendered runtime environment file. The source template for it didn't exist anywhere in the repository -- `terraform plan` would have failed the first time this code path was exercised. A minimal template was created using only the variables already being passed into it (`project_name`, `environment`, `service_name`, `database_workspace`, `aws_region`, `ecr_registry_url`, `enable_ecr_access`, `core_root_secret_arn`) -- nothing about your actual runtime needs was invented, review and expand it. It's named `env.tftpl`, not `.env` -- this repo's `.gitignore` has a blanket `.env` rule (sensible for typical app secrets) that would otherwise silently discard this file, by filename alone, on every commit regardless of its actual content.

**A deprecated `aws_region` attribute.** `data.aws_region.current.name` was deprecated in AWS provider `6.0.0` in favor of `.region` -- confirmed against the provider's own changelog. This module uses `.region`.

**Password exposure via CLI arguments, in `provision.sh`.** MySQL and MongoDB credentials were passed as `-p<password>` command-line arguments to their respective clients -- visible to anything that can read that container's process list for as long as the command runs, a well-documented anti-pattern MySQL's own client explicitly warns about. Fixed via environment variables on the `docker exec` call itself (`MYSQL_PWD` for MySQL; for MongoDB, which has no direct equivalent, the piped script's own first line authenticates by reading the variable through mongosh's Node.js `process.env`) -- the same class of protection, applied consistently across both engines.

**A `set -e` bug found by actually testing the fix above**, not by reading the code: a failing `jq` lookup inside a bare command substitution aborts the whole script immediately under `set -e`, bypassing the intended clear error message entirely. Fixed by disabling `-e` around just that one call and checking its exit code explicitly.

### Connection limits

Each login may hold only so many connections open at the same moment: a service's own login its entry in `service_exceptions` or `service_default`, every person's login `person`, each counted separately. `provision-service.sh` reads `/<project>/database/connection-limits` once per run and passes the numbers on; `provision-people.sh`, when core's apply sends it on its own, reads the parameter itself. Core's SQL sets them with `ALTER ROLE ... CONNECTION LIMIT` (PostgreSQL) and `ALTER USER ... WITH MAX_USER_CONNECTIONS` (MySQL); MongoDB has no per-login limit. The administrator (`postgres`, `root`) is never capped.

A parameter rather than the host's `.env`: the `.env` is part of the user data, and changing it would restart the database host. So a changed number needs no restart and no script refresh; it applies the next time the login is provisioned. A missing parameter or a number that is not a whole number from 1 to 10000 stops the run before anything reaches an engine.

### The administrator password

The engine images read their administrator password (`root_password` in this module's secret) only when their data folder is first created, so a replaced password would never reach a running engine by itself. `sync-admin-password.sh` makes each running engine's administrator password the secret's current one:

| Engine | How |
| --- | --- |
| PostgreSQL | Set every run, over the container's local socket, where the image trusts `postgres` without a password |
| MySQL, MongoDB | Nothing if the current password works; otherwise it signs in with the secret's previous version (`AWSPREVIOUS`, which Secrets Manager keeps whenever the value changes) and sets the current one |

It runs at the end of core's apply (the `<project>-database-provision-people` document runs it before the people step) and in `provision-service.sh` before a service is provisioned. A password matching neither version (replaced twice before the host saw it, or changed by hand) stops the run with a message; the runbook's *Changing an administrator password* says how to recover. Tests: `modules/platform/host-scripts/tests/test_sync_admin.sh` (offline) and `test_sync_admin_real.sh` (real PostgreSQL and MySQL).

## Ownership of the scripts

This module owns its scripts (`assets/`) and uploads them to the deploy bucket beside the shared deploy library from the `platform-scripts` module. Its user data (`assets/bootstrap.sh`) is small on purpose -- EC2 caps user data at 16 KB -- and only prepares the volume, installs the runtime `.env`, fetches the verified scripts and runs the first deploy.

## Provisioning a service's database

A service does not create its own database. Its infrastructure repository publishes a request and sends the `<project>-database-provision` document; this host does the rest.

```text
service's infra repo                     database host
  publishes  provisioning/<service>/config.json   ->  provision-service.sh
             provisioning/<service>/extra.sql (optional)   fetches, checks, runs:
  sends      <project>-database-provision              provision-<engine>  (as the administrator)
                                                       extra.sql           (as the SERVICE's user)
```

**Core owns the SQL.** `assets/provisioning/provision-postgres.sql`, `provision-mysql.sql` and `provision-mongodb.js` create the database, the user, its password and its grants, so every service is provisioned the same way and none writes its own `CREATE DATABASE`. They are installed and checksum-verified with the rest of the host's platform scripts.

**The extra file runs as the service's own user, on its own database.** Run as the administrator, one line of a service's SQL would have full control of every other service's data on the same engine.

**It runs on every apply.** Terraform triggers it each time, so every step is conditional and the password is set each time, which is what makes a rotated secret heal itself.

**The request holds no credential.** It names the service, its engine and its secret's ARN; this host reads the secret itself. Before any SQL runs, the name, user and password are checked against the alphabet core generates them from, so a value carrying a quote cannot end a string and begin a statement of its own.

Managed databases are not covered: there is no container to run provisioning in, and that mechanism does not exist yet.

```text
database/

│                       database-update and refresh SSM documents, SSM parameter, auto-recovery
│                       alarm, DNS record, DLM backup policy

├── outputs.tf
├── assets/
│   ├── env.tftpl        -- runtime env template
│   ├── bootstrap.sh     -- user data: data volume, workspace, .env, fetch scripts, first deploy
│   ├── update.sh        -- syncs the platforms team's registry and engines and runs them
│   ├── provision.sh     -- creates a service's database and user inside an engine
```
