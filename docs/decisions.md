# Decision log

The decisions that shape this blueprint, each with the reason, so a future reader does not have to reconstruct them. Newest concerns last within each group.

## Layout

| Decision | Why |
| --- | --- |
| `modules/` holds four infrastructure domains (network, edge, compute, database) plus `platform/` | The domains mirror the architecture; everything else — who may deploy, the contract, the shared scripts — is not infrastructure and would otherwise flatten that shape into a dozen sibling folders |
| A module used by exactly one domain is nested inside it (`edge/cloudfront`, `network/nacl-security`) | They are that domain's own composition, not a shared building block |
| Moving a module's files does not move anything in state | A resource's address comes from the module **call** name, not its source path |

## Blueprint

| Decision | Why |
| --- | --- |
| Repository name and IDs are variables, supplied by the caller and never committed | Many projects clone this repository; nothing project-specific may be baked in. CI passes them from the GitHub context |
| Values that differ per project ship as `CHANGE_ME`, with format validation and a CI guard | A clone must not reach AWS half-configured, or point at a domain nobody owns |
| One AWS account per environment | Limits any mistake to one environment. So SSM paths and IAM names carry no environment segment; global names (S3 buckets) still do |
| The Terraform version lives in `.terraform-version` only | One place to change; CI and the bootstrap script read it |
| Default assets are this repository's `assets/` folder; an external repository is optional | A clone works without a second repository or a long-lived token |

## Identity and access

| Decision | Why |
| --- | --- |
| Trust GitHub Environment subjects (`<env>`, `<env>-plan`), not branch or pull-request subjects | Every job declares an environment, and then GitHub issues an environment subject; the OIDC module's defaults never matched |
| Immutable subject format (numeric IDs) by default, with a classic switch | A renamed or transferred repository cannot be impersonated by someone who later claims the old name |
| One administrator role per account, guarded by GitHub Environments | A role that creates IAM roles can grant itself anything, so trimming its policy buys little; who can run a job as it is what matters. `<env>-plan` lets plans be guarded separately from applies |
| A service has two repositories, infra and app, and two roles | The repository that creates resources and the one that deploys the application have different jobs; giving each only its own means the app's CI can never create or change a resource, and only the infra role ever holds IAM |
| Service roles are generated from `service_name`, `kind` and `tier`, scoped to that service's own resources | Isolation between services without hand-written policies. What AWS cannot scope is documented in `modules/platform/service-roles/README.md` |
| In staging and production each service creates its own hosts, under a permissions boundary | Per-service compute isolates services and lets staging and production be sized differently from development. Creating an instance role is a privilege-escalation path, so the infra role can only create roles that carry the boundary and a `Service` tag, confined to `/services/<service>/`, and can never remove either |
| The boundary uses `${aws:PrincipalTag/Service}` and lives at `/platform/` | One policy confines every service's instance role to its own resources; the path keeps it out of the namespace services may create policies in |
| The names `database`, `database-hub`, `fleet`, `internal`, `platform`, `private` and `services` are reserved | A name-pattern permission on `<project>-<service>-*` would otherwise reach core's own secret and SSM documents |
| Services redeploy with a custom SSM document, never `AWS-RunShellScript` | Permission to send `AWS-RunShellScript` is root on every host |
| Service roles are a separate instance of the OIDC module | The first apply targets only the core role; anything it depends on is built too, and the service roles depend on the whole environment. A test enforces this |
| Role ARNs are published to a `platform-outputs` branch, not `main` | `main` stays pull-request-only, with no bypass rule and no bot commits |

## Platform

| Decision | Why |
| --- | --- |
| The infra role writes `/<project>/services/<service>/config` and the app role reads it | The only handoff between a service's two repositories; neither needs the other's permissions |
| Services read one SSM parameter, not core's Terraform state | State contains every generated secret; a service role that could read it could read them all |
| No CloudFront secret header | The ALBs are internal, reachable only through the CloudFront VPC origin |
| Static files live under `static/<service>/` in the shared assets bucket | Reuses CloudFront's one `/static/*` behaviour, so onboarding a service never changes CloudFront |
| Only 502, 503 and 504 map to custom error pages | Custom error pages apply to every origin; mapping 404 or 500 would replace applications' own pages and JSON errors |
| The shared fleets do not own their target groups (`manage_traffic_sources = false`, autoscaling v3) | An ASG's target groups are an attribute of the group, so a service attaching its own from its own repository reads as drift here; before v3 the next core apply removed it, taking every service on the tier out of its load balancer |
| Core builds one golden AMI per environment; services never build their own | Patching decides it: a CVE fix is one rebuild rather than one per service, and nothing in a container host varies per service. It also keeps Image Builder, `ec2:CreateImage` and `iam:PassRole` out of every service's policy and out of the boundary |
| The contract carries the AMI parameter's NAME, not the ID | A service's launch template reading the parameter picks up a rebuild on its next plan; an ID copied once would freeze it on whatever was current that day |
| Core owns the deploy scripts for dedicated hosts too | Same argument: a fix to the deploy library is one upload, not one change per service repository. The boundary lets a host read `_platform/` in core's bucket and nothing else in it |
| Shared fleets use EC2 health checks | With ELB checks one failing service makes the group replace a host that runs every co-tenant |
| Database engines are defined by the platforms team; each opens its own port | One engine per type is shared by every service (a database and user each), published on its native port as on RDS. The platforms team decides which engines exist, so core does not open their ports |
| Core owns the provisioning SQL; a service may add an extra file | Every service's database, user and grants are created the same way, and no service writes its own CREATE DATABASE. The extra file runs as the service's own user on its own database: as the administrator, one line of a service's SQL would control every other service's data on that engine |
| Provisioning runs on every apply and is conditional throughout | Terraform triggers it each time, so it must be safe to repeat; setting the password each time is what makes a rotated secret heal itself |
| A service's infra role can send the provisioning document naming another service | IAM cannot condition `ssm:SendCommand` on a parameter's value. It is harmless: it re-runs that service's own published request, which is idempotent |
| Staging and production use an RDS instance, one per engine, shared by every service | An RDS instance runs exactly one engine, chosen at creation; a database per service on one instance matches the development hub and costs a fraction of an instance each |
| Every engine is declared in staging and production; none runs until listed in that environment's `database_engines` | Cost: an engine nobody uses must cost nothing. The list is per environment, so staging can run fewer engines than production |
| MongoDB runs on one DocumentDB cluster per environment (`terraform-aws-documentdb`), 1 instance in staging and 2 in production | The data is always stored in three zones; a second instance keeps it available through an instance or zone failure, which is production's Multi-AZ decision |
| Every MongoDB user, in every environment, lives in the `admin` database with `readWrite` on its own database | DocumentDB keeps all users in `admin` whatever is asked; development does the same so an application authenticates with `authSource=admin` everywhere |
| The provisioning function verifies every database's certificate and host name against AWS's RDS certificate bundle, committed in the repository | Encryption alone would hand the administrator's password to anything able to impersonate the database; the bundle is committed rather than fetched because the function runs in the isolated tier, with no route to fetch it. Missing, the plan stops (precondition) and CI fails (`check-ca-bundle.sh`) |
| The provisioning function vendors pymongo with its compiled parts removed | Pure Python runs on any Lambda architecture; the C extensions only speed up encoding, which provisioning barely does |
| Staging's instances are `always_on` by default, or `working_hours` | Cost is the reason to stop them, availability the reason not to; the choice is one tfvars value. Production has no such setting |
| Working hours stop the instances every day, not only on running days | An instance started by hand, or restarted by AWS after 7 days stopped, is stopped again that evening |
| The schedule calls RDS through EventBridge Scheduler, with no Lambda | Nothing to write, package or patch, and effectively free at this scale |
| Development's shared fleets default to 1 instance per tier (at most 2), on demand | Cost: 8 instances were about $315 a month, 2 are about $79; development tolerates a few minutes' outage while a failed instance is replaced |
| Development and staging use a NAT instance (`nat_type = "instance"`, `terraform-aws-nat-instance`); production a NAT Gateway | A t4g.nano instance costs a few dollars a month with no per-GB charge, against about $43 plus about $0.06 per GB; its outbound traffic stops for the minutes it is recovered or replaced, acceptable outside production |
| The NAT instance is one instance with EC2 automatic recovery, not an Auto Scaling group of one | A group would have to move a network interface onto each new instance at boot, which is fragile and untestable without AWS; recovery keeps the same interface and Elastic IP, and a rebuild updates the routes in the same apply |
| The internal tier is off by default in every environment (`internal_tier_enabled`) | Its load balancer bills every hour with or without a service behind it (about $21 a month), and development's internal fleet about $39 more. Off, the contract offers no internal tier, so a service asking for it fails its plan and says why |
| Switched off, development's internal fleet is held at zero instances rather than removed | The group, launch template and permissions stay, so turning the tier on is a change of three numbers, not a rebuild |
| The interface endpoints admit the private, internal and isolated tiers | Private DNS sends every host's call to the endpoint; admitting only the isolated tier left the fleets unable to reach SSM, ECR, Secrets Manager or Logs |
| Staging and production create only the Secrets Manager interface endpoint | Their isolated tier needs nothing else; each endpoint left out saves its hourly charge, and the hosts reach the other APIs through the NAT, which is cheaper at this platform's traffic |
| The administrator is `platformadmin` on every managed engine | RDS allows at most 16 characters and DocumentDB letters and digits only; a name built from the project could break either |
| Aurora and Multi-AZ DB clusters are not in `terraform-aws-rds-instance` | They are `aws_rds_cluster`, a different resource with different arguments and two endpoints; hiding both behind a `count` would leave half the variables inert in either mode |
| The RDS instance is a published `terraform-aws-rds-instance` module; only the provisioning function stays in core | The instance is generic and any project could use it; the function knows core's service-secret naming and is invoked by core's generated roles, so publishing it would bake platform policy into a reusable building block |
| The published module takes the administrator credential rather than generating one | A module that generates a password owns it, and the caller then has to discover where it went instead of keeping it with its other secrets |
| A managed database is provisioned by a Lambda inside the VPC | There is no container to exec into and no route from a CI runner to the isolated tier. The function derives the secret's name from the service's, so a caller cannot target another service's credential |
| The Lambda's PostgreSQL driver is committed to the repository | The Lambda runtimes carry none, and a compiled one would have to match the runtime's architecture; `pg8000` is pure Python |
| The isolated tier gained a CloudWatch Logs endpoint | It has no route to the internet, so without it anything running there writes no logs at all and a failure is invisible |
| The two provisioning paths are mutually exclusive in the contract | An environment has either an EC2 host with a document or a managed instance with a function, never both; a precondition enforces it |
| An engine stops only on an explicit `active: false` | A database must never stop because a file disappeared |
| Scripts live in S3, verified against an SSM checksum manifest | EC2 caps user data at 16 KB; checksums in SSM mean a script edit never restarts a host |
| The compose guard is a best-effort deny-list, not a security boundary | It stops mistakes, but a team that writes a compose file is still trusted. Real isolation is one host per service (dedicated ASGs in staging and production) |
| Dedicated hosts wear their tier's security group as well as their own, and the contract publishes it for every tier | The databases and the VPC endpoints admit the tier's group, so hosts wearing only their own group could reach neither their database nor Secrets Manager. The tier group has no inbound rules, so wearing it opens nothing on the host. Chosen over admitting the tiers' CIDR ranges, which would let in anything placed in those subnets and tie the rules to the address plan |
| The team's own tools (database GUIs, later others) run on hosts of their own and wear a `team-tools` security group, which the databases and the VPC endpoints admit | Tools are not customer-facing: a problem in one should not be able to reach the customer fleets, or the reverse. A group of their own, rather than the private tier's, lets the databases admit the tools without admitting the tools to anything that trusts a customer tier. A fifth subnet tier or a separate account would isolate further, at the cost of a network redesign or cross-account peering |
| `for_each` is keyed by fixed names, never by IDs Terraform creates in the same apply | An ID is unknown until apply, and Terraform refuses to plan a `for_each` whose keys it cannot know, so a set of new security group or subnet IDs fails the first plan of a fresh environment |
| Database access for people has three levels: a service's **agents** (`<service>.<name>`, declared in the service's repository, that service's database only), the **platform list** (`platform.<name>`, core's `data/people.json`, every service's database), and each engine's **administrator** for emergencies | The team that owns a service's data decides who sees it, and an agent can never reach another service. The owner and trusted staff still reach everything under their own name, so actions are traceable; the administrator login, which is not, stays sealed. A login contains a dot, which a service's user never does, so no service name has to be reserved for people |
| Every person's database password is in ONE secret per environment, read only by administrators, who hand each person their own | One secret per environment instead of one per person per environment: a few cents rather than dollars, and one place to look. The fleets are denied it with the other platform database secrets |
| Service names beginning `database-` are reserved, and the fleets are denied every `<project>-database-*` secret | The platform's database secrets (the hub's, each engine's administrator's, the people's) share that prefix. Reserving only exact names left `database-admin-mysql`, a valid service name, able to claim the MySQL administrator's secret name and permission pattern |
| The team tools' web addresses sit behind a Cognito user pool (Essentials tier) with an authenticator app always required and no self sign-up | Everyone in `people.json` gets a sign-in; nobody else can. Essentials is free up to 10,000 monthly active users and its managed login sets up the authenticator at first sign-in. SMS costs per message, and email codes would share an inbox with password reset. Cognito's own email sender is enough for a team's invitations |
| Services **declare** their agents' emails (`front-door/<service>.json` in the deploy bucket) and a core function makes the Cognito users match every declaration; no service role touches Cognito | Permissions on a user pool cannot be limited to some of its users, so a service allowed to add its own people could remove anyone's. Each service's role may write only its own declaration. The function acts on the whole picture or not at all: a declaration it cannot read stops it, rather than delete the sign-ins it names |
| People's logins are made to match their list exactly, scope by scope: a service's agents whenever that service is provisioned, the platform list at the end of every core apply and after every service is provisioned | One source of truth per scope, applied in full each time. Which logins belong to a scope is decided by an exact pattern, never by LIKE: `_` in a service's name is a LIKE wildcard, and removing `ab_c`'s agents must never reach `abxc`'s |
| PostgreSQL gives each scope two groups (`<scope>.group_read`, `<scope>.group_write`) with default privileges; MySQL grants each person directly on each database; MongoDB uses `read` / `readWrite` on the service's database (agents) or `readAnyDatabase` / `readWriteAnyDatabase` (platform) | Only default privileges cover tables a service creates later in PostgreSQL; MySQL's database-level grants already do. Granting a role in MySQL needs ROLE_ADMIN, which the RDS master user may not have; direct grants need only what it has |
| Each login's password and access level are kept in a secret: the platform list's in core's people secret, a service's agents' in the service's own secret (its `agents` entry) | The staging and production functions run in the isolated tier, whose only AWS endpoint is Secrets Manager |
| In production a service's agents are read-only unless core lists them in `data/agent-write-exceptions.json`; the platform list may write | No one damages live data from a GUI by default, and a service cannot grant itself write: an exception goes through core's production review. The platform list is itself approved there. A service asking for unapproved write fails its provisioning, rather than being quietly given read |
| Every login on a shared engine has a cap on connections held open at once: each service's own login core's `service_default` for the environment, or an exception core approves, and every person's login a small fixed `person` cap (development 20, staging 15, production 50; 5 per person). From `data/connection-limits.json`, set on every run like the password; the administrator is never capped | Every service shares each engine, and the engine has one total. One service's connection leak, or a forgotten GUI, could otherwise use it up and cut every other service off at once. Core decides the numbers so that no service can raise its own share. The caps are ceilings, not reservations: the engine's size still decides the total. MongoDB and DocumentDB have no per-login limit, so there they are documented only. Development's host reads them from an SSM parameter, because its `.env` is part of the user data and changing it would restart the database host |
| Each service CI role's permissions are managed policies, 8 statements each, under `/platform/service-roles/`, instead of one inline policy | A dedicated infra role with three engines and the front door needs about 10,300 to 10,700 characters, over IAM's 10,240 for a role's inline policies, so every such service would have been refused at plan. The split is by number of statements, not length, so the number of policies is known at the first plan, and each role receives its policies' ARNs as built strings for the same reason. They sit outside `/services/<service>/`, where a dedicated infra role may change policies, so no role can change its own permissions |
| A replaced administrator password reaches every engine: RDS applies it at once by itself, DocumentDB because core sets `apply_immediately` on it, and development's engines through `sync-admin-password.sh`, which signs in with the secret's previous version and sets the current one, at the end of core's apply and before each service's provisioning | The secret changes the moment the apply does, and everything that signs in as the administrator reads it there. DocumentDB otherwise applies a new master password only in its weekly maintenance window, and the development images read theirs only when first created, so provisioning would be refused for up to a week, or for good. `apply_immediately` also applies DocumentDB's other changes (such as a new instance class) at the end of the apply that makes them, which a deliberate apply means anyway. Secrets Manager keeps one previous version, so one replacement per apply is supported; two before the host sees either needs the runbook's recovery |
| A staging database stopped outside its working hours is skipped by the people step, with a warning, rather than failing the apply | The apply itself succeeded; the **Provision people** workflow applies the people once the database is up |
| Invariants are preconditions, not `check` blocks | A failed `check` only warns and the plan continues |
| Generated secrets use only letters, digits and `-_.` | Characters such as `$` and `#` are corrupted by the env files the values pass through |
| Every environment folder commits its provider lock file, and CI enforces it | `terraform init` writes the lock file locally and nothing complains that it is untracked, so it is easy to leave out. A test step fails when one is missing or does not lock a provider the folder declares, and plan, apply and destroy run `init -lockfile=readonly`, which also refuses a lock file missing a provider only a module declares |

## Naming

| Decision | Why |
| --- | --- |
| Every resource that belongs to a service is `<project>-<environment>-<service>-<resource>`; anything else is `<project>-<environment>-<resource>` | One order, and it is the one 16 of the 18 published modules already use. Two orders disagreeing once produced a real bug: a policy scoped to one order denying a group named in the other |
| Names that never leave the account (SSM documents and parameter paths) omit the environment | The account is the environment; buckets and IAM names include it because they are global or shared across accounts |
| **Exception:** the secret and the target group are `<project>-<service>-<environment>-...` | `terraform-aws-secrets-vault` and `terraform-aws-target-group` v1 name them that way. The order becomes uniform when both release a v2. Until then the exception is one local, `service_first_prefix`, in `service-roles`, and one pattern each in the boundary, the provisioning function and the shared fleet's secret policy |
| `fleet` names only what belongs to the shared fleet (`fleet-update`, the fleet's secret and deploy-read policies) | Artifacts both hosting models use are `platform` or `deploy`: the bucket is `<project>-<environment>-deploy` and the manifest is `/<project>/platform/scripts-manifest`. The old names implied a fleet where dedicated hosts have none |
| The hosting models are `shared` and `dedicated` | The old `shared-fleet` named a mechanism where `dedicated` named an exclusivity, so the pair did not read as a pair. Changed before the contract was first published, so no schema bump |
| Two module folders named `scripts` became `compute/deploy-bucket` and `platform/host-scripts` | Each now says what it is, and no folder shares a name with another |
| "Registry" is always qualified: the **port registry** (the platforms team's repository) and the **ECR registry** (container images) | The unqualified word meant two different things in the same repository |
| The provisioning function grants itself the service's role before creating its database | RDS's administrator is a member of `rds_superuser`, not a true superuser, and PostgreSQL refuses to create or reassign a database to a role its creator cannot become ("must be able to SET ROLE"). Found by running the SQL against a real PostgreSQL as a non-superuser admin; every fake-cursor test had passed |
| The team-tools repository gets its own generated CI role (`tools-role`), scoped by the `Service=team-tools` tag, its Auto Scaling group's name and `/services/team-tools/` with core's permissions boundary | The tools run on hosts of their own in every environment, so the role holds the dedicated-hosting permissions everywhere, plus load-balancer rules and a Cognito app client where there is a front door. A separate module, like `engines-role`, keeps it out of the service roles, whose dedicated policy is already near IAM's 10,240-character limit. `team-tools` is reserved as a service name |
| Development creates the permissions boundary too, and publishes it in its contract | Services share fleets there and create no roles, but the team tools' instance role must carry it. Services read it only for dedicated hosting |
| Each load balancer's security group has an explicit allow-all outbound rule | Terraform removes AWS's default outbound rule when it creates a security group, so a load balancer's group without one could reach neither its targets nor, for a sign-in step, the identity provider. Inbound stays restricted (CloudFront's prefix list; the private tier for the internal one) |
| The isolated tier may start connections within the VPC and, over HTTPS, to S3's prefix list; its network ACL allows HTTPS out and the replies back from anywhere | A security group decides which connections an instance may start, so with none the database host could reach no VPC endpoint (SSM, ECR, Secrets Manager) and the functions no secret. S3's gateway endpoint is reached at S3's own addresses, which an ACL cannot name as a prefix list; the isolated route table has no internet or NAT route, so the ACL's 0.0.0.0/0 reaches S3 alone |
| The provisioning functions also wear the isolated tier's security group | The Secrets Manager endpoint admits the tier groups, and the function's own group (which the database's rule names) has no outbound rule of its own |
| A project runs any one, two or all three environments, listed in `environments.json`; every workflow and script reads it through `scripts/ci/enabled-environments.sh` | A small project may afford only production, or development and production. The unused folders stay, ignored, so adding one later is a line and a bootstrap. Plans, applies, destroys and provisioning refuse or drop anything unlisted, so a change can never reach an account that was not set up |
